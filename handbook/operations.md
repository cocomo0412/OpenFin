# OpenFin 운영 매뉴얼

작성일: 2026년 10월 3일 · 수정일: 2026년 10월 6일 · 버전 1.5.0 · 관리 담당: 배포·운영 담당과 프로젝트 총괄 PM

버전 변경 기준과 이력은 [매뉴얼 변경 이력](CHANGELOG.md)을 따른다.

정기 자료 갱신은 사용자가 선택한 **매주 화요일과 금요일 오전 9시, 한국시간**을 기준으로 한다. 수집 결과를 검사하고 검토한 뒤 서비스에 반영한다. 이 문서는 운영 기준을 정한 것이며 자동 실행 예약을 활성화한 것은 아니다.

자료 구축과 정기 갱신은 **공식 API 요청**을 원칙으로 한다. API가 없거나 실패한 항목을 웹 수집으로 메우지 않는다. API 미제공은 대상 제외로, API 오류는 실패·보류로 구분해 기록한다. 기존 자료와 원래 날짜는 보존하고, 예외 수집은 사용자가 범위를 별도로 명시했을 때만 진행한다.

## 1 주 2회 갱신의 적용 범위

화·금 오전 9시를 기본 운영 일정으로 정한다. 수집·검토 부담을 나누면서 자료를 정기적으로 확인할 수 있지만, 점검 사이에 3일 또는 4일의 간격이 생긴다. 실시간 금리나 모든 제도의 현행성을 보장하는 주기로 설명하지 않는다.

| 자료 | 정기 회차에서 할 일 | 별도 검토 |
| --- | --- | --- |
| 예금·적금 등 연결된 금융 API | 전체 페이지 수집, 상품 식별자와 공시 필드 비교 | 금리·대상·판매상태의 의미와 누락 사유 |
| 정부 지원과 대출 등 연결된 공공 API | 기존 수집 계획에 따라 수집·검사 | 지원 대상·신청기간·중복 제한 변경 |
| 통계와 기준자료 | 제공기관이 공개한 기준 기간을 확인하고 수집 | 월·분기 통계를 오늘 자료로 해석하지 않음 |
| 세금·공제, 법령, 약관 등 | 공식 API가 연결된 범위만 갱신하고 나머지는 미제공·미연결로 기록 | 기존 자료의 출처와 날짜 유지, 웹 수집 확대 제외 |
| 개념·용어·관계 | 정의나 출처 변경이 확인된 경우 검토 | 매 회차 상품 수집 대상과 구분 |

법령 개정, 중요한 조건 변경, 잘못된 안내, 서비스 장애를 **확인한 경우** 정기일까지 기다리지 않고 해당 범위를 우선 처리한다. 이는 별도의 실시간 감시가 이미 작동한다는 뜻은 아니다.

초기 4주간 회차별 소요 시간, 요청 실패, 미갱신 사유, 발견된 중요 변경을 기록한 뒤 주기와 수집 범위를 재평가한다. 이 기간과 재평가 방식은 운영 제안이며 자동 일정은 아직 없다.

## 2 팀 책임과 완료 판정

| 담당 | 운영 책임 |
| --- | --- |
| 프로젝트 총괄 PM | 우선순위·일정·범위 결정, 담당 배정, 완료 판단과 사용자 보고 |
| 화면·사용자 경험 | 홈·정보검색 일관성, 검색 흐름, 모바일·접근성, 화면 구현 |
| 금융자료·온톨로지 | 공식 API 규격·수집 범위, 분류·관계, 출처·기준일·누락 검증 |
| 서버·MCP 개발 | 수집·가공 도구 및 MCP 유지보수, 오류 원인 분석·수정, 실행 기술 지원 |
| 개발보안 | API 키 보호, 인증·권한, 입력·출력, 의존성, 공개 자료 노출 검토 |
| 독립 품질검증 | 문제 재현, 회귀 검사, 보안 조치 재검증, 배포 전 통과 여부 판단 |
| 배포·운영 | 정규 수집·빌드 회차 운영, 홈페이지·MCP 배포 구분·실행, 운영 확인·복구 및 증적 관리 |

총 7개 역할로 운영한다. 기존 개발보안의 독립 검증은 독립 품질검증 담당에 통합하고 배포·운영 담당을 별도로 둔다. 역할 수와 동시 실행 인원은 다르며 작업 범위와 실행 환경에 맞춰 배정한다.

동일 작업의 구현과 최종 품질·보안 검증은 서로 다른 담당이 수행한다. 화면·사용자 경험 또는 개발보안 담당이 직접 수정한 코드도 독립 품질검증 담당이 검토한다. 독립 품질검증 담당이 수정에 참여하면 다른 담당을 독립 검증자로 배정하고 검증 전까지 대기 상태로 기록한다. 배포·운영 담당은 실제 실행·운영 확인을 맡고 검증 실패를 임의로 통과 처리하지 않는다.

중요 보안 발견 사항은 프로젝트 총괄 PM이 영향과 실제 운영 도달 여부를 확인해 우선순위를 정한다. 노출이 의심되는 비밀값은 문서에 복사하지 않는다. 키 폐기·재발급, 공개 파일·이력 정리, 홈페이지·MCP 재배포는 필요한 조치별로 구분한다. 날짜별 코드 검토 기록은 `reports/code-review/`에서 관리하며 검토 완료와 조치 완료를 구분한다.

일상적인 회차는 정한 범위와 기존 권한 안에서 처리한다. 새로운 데이터 범위, 유료 전환, 비교·추천 기능 개방 등은 별도 결정 사항으로 분리한다. AI 담당의 검토만으로 공식 법령 해석을 확정하지 않는다.

## 3 기존 기능과 자동화 상태

| 기능 | 현재 구현 | 주의점 |
| --- | --- | --- |
| 전체 자료 갱신 | `npm run knowledge:refresh` | 수집부터 원본 통합·공개 파일 생성까지 로컬 파일을 변경함 |
| 실패 요청 재시도 | `npm run knowledge:retry-failed` | 일부 수집 재시도만 하며 통합·빌드·배포를 끝내지 않음 |
| 출처 변경 점검 | `track-sources.mjs` | API와 웹 출처가 섞여 있어 전체 실행은 기본 정기 절차에서 제외 |
| 출처 점검 Actions | `Track OpenFin Sources` | 수동 도구가 남아 있으나 현재 범위 전체를 정기 예약하지 않음 |
| MCP 운영 배포 | `OpenFin MCP pipeline` | MCP 관련 경로 변경이 main에 반영될 때 검증과 배포 |
| 화·금 9시 갱신 | 이 문서의 합의 일정 | 자동 예약과 실행 환경은 아직 설정하지 않음 |

두 가지 사전 확인 명령은 의미가 다르다. `refresh-all.mjs --dry-run`은 실행할 단계 목록만 출력한다. `track-sources.mjs --dry-run`은 실제 출처에 네트워크 요청을 보내지만 상태 파일과 확인 이력을 변경하지 않는다. 보고서 디렉터리를 지정하면 점검 보고서는 작성한다.

## 4 회차 시작 전 확인

1. 기준 브랜치와 현재 변경사항을 확인하고 이번 회차용 독립 작업 공간을 준비한다. 검증되지 않은 이전 변경과 섞지 않는다.
2. 직전 정상 반영 커밋과 홈페이지·MCP 배포 기록을 기록한다.
3. 필요한 API 키가 승인된 실행 환경에 설정되어 있는지 확인한다. 보고서에는 존재 여부만 기록한다.
4. 같은 작업 공간에서 다른 갱신이 실행 중인지 확인한다. 현재 파일 잠금은 해당 작업 공간에만 적용되므로 다른 작업 공간과의 중복도 조정한다.
5. 실행 전 변경사항과 이전 성공 수집본을 보존한다. `.api-candidates/`는 Git 제외이므로 커밋만으로 수집본까지 백업된다고 가정하지 않는다.
6. 처음 실행하는 환경이라 이전 정상 수집본이 없으면, 일부 API 실패 시 통합이 중단될 수 있음을 감안해 환경을 준비한다.

설치와 키 준비는 [개발 매뉴얼](development.md)을 따른다. 아래 명령은 저장소 루트에서 하나씩 실행하고 결과를 확인한다.

## 5 정기 갱신 실행

### API 대상 점검

수집 계획의 출처·요청 경로·인증·조회 기간·페이지 조건을 확인한다. 공식 API가 연결되지 않은 출처는 이번 회차 범위에서 제외하고 미제공 또는 미연결 사유를 남긴다. 실행 후 API별 응답과 오류, 항목별 변경 여부를 수집 결과에서 확인한다.

기존 `track-sources.mjs`의 전체 registry 점검에는 웹 출처가 포함되므로 기본 정기 절차에서 제외한다. 이전 버전의 전체 출처 `--force` 명령을 화·금 갱신에 사용하지 않는다. API 출처만 검사하는 보조 점검을 추가하려면 대상 목록과 실제 요청 경로가 공식 API인지 먼저 검증한다. 기존 도구와 workflow를 삭제하거나 변경한 것은 아니며, 사용 범위를 이 운영 기준으로 제한한다.

### 자료 수집과 통합

정규 갱신·검증 빌드는 실행 전 이전 산출물과 수집 스냅샷을 백업하고 복구 기록을 남긴다. 충분한 백업 공간을 확보한다. 단계 실패 시 이전 정상 묶음으로 복구하며, 강제 종료되어 기록이 남았다면 같은 진입점의 다음 실행에서 중단된 프로세스가 끝났는지 확인한 뒤 복구한다. 다른 수집·빌드를 동시에 실행하거나 복구 기록·백업을 직접 지우지 않는다. 복구 실패가 보고되면 해당 작업 파일을 배포하지 않고 원인을 확인한다. 성공 확정 이후 백업 정리만 실패한 경우에는 정상 결과를 되돌리지 않고 남은 정리를 재시도한다.

개별 inventory·integrate 스크립트의 직접 실행은 파일별 안전 쓰기만 제공하므로 운영 회차는 아래 정규 진입점을 사용한다. 날짜와 원자료를 복구하는 과정은 최신 API 자료를 새로 수집했다고 기록하는 과정이 아니다.

백업·복구 준비 중 강제 종료되어 recovery claim이 남거나 실행 직전의 하위 작업 PID가 확인되지 않는 경우에는 자동 복구를 중단한다. 작업 프로세스와 백업을 확인한 후 [운영자 복구 절차](../reports/code-review/2026-10-06/remediation-01/pipeline.md)를 따른다. 임의로 잠금을 지워 재실행하지 않는다.

```powershell
npm run knowledge:refresh -- --dry-run
npm run knowledge:refresh
```

실제 갱신은 공식 API 수집, 목록 정리, 기존 항목 연결, 원본 지식 통합, decision 관련 산출물 생성·검증, 공개 파일 빌드, 일부 검사, 무료 MCP 카탈로그 생성을 수행한다. 단순 후보 저장 명령이 아니며 실행 후 `knowledge/`, `docs/`, `reports/`, `mcp/src/free-catalog.json` 등의 차이를 검토한다. 자동 push나 배포는 하지 않는다.

이 명령에 포함된 검토 기록 생성·승격 조건 검사가 사람의 내용 검토나 무료 서비스의 추천 기능 개방을 뜻하지 않는다. 비교·추천 제한과 검토 범위를 확인한다.

### 결과 확인

다음 산출물을 함께 확인한다.

- `.api-candidates/refresh-pipeline-run.json`: 단계별 성공·실패와 소요 시간
- `.api-candidates/api-refresh-run.json`: 공공 API 요청별 결과
- `.api-candidates/finlife-additional.json`: 개별 수집일과 `failures`. 실패가 있어도 이 단계가 정상 종료할 수 있음
- `docs/opentax/collection-inventory.json`: 수집 범위와 `pending` 보류 요청
- `docs/opentax/canonical-refresh-report.json`: 통합 결과와 `unresolved`, `remaining_domains`
- `reports/refresh/README.md`, `reports/refresh/current.json`: 미반영 항목의 이유와 후속 조치
- `.api-candidates/pipeline-*.log`: 실패 단계의 상세 기록

공공 API 단계는 일부 실패를 허용하고 계속될 수 있다. 따라서 최종 `completed`나 `validated`, 명령 종료 코드 0만으로 전체 출처 갱신 성공을 선언하지 않는다. 요청 오류 수와 미갱신 항목 수를 더하거나 서로 같은 단위로 해석하지 않는다.

날짜도 필드 이름만 보고 해석하지 않는다. 현재 통합 코드의 `reviewed_at`은 API 식별자·필드 매핑 검토 범위이며 법령·약관 전체 검토일이 아니다. 일부 `validated_at`에는 별도 검사 실행 시각 대신 수집 시각이 들어가므로, 실제 검사 시각은 회차 실행 기록으로 확인한다. 통계의 최신 기간 자동 탐색도 일부 응답과 이전 필터를 이용하므로 기간이 계속 멈춰 있다면 기관 공시 범위와 정렬을 별도 확인한다.

## 6 실패와 재시도

```powershell
npm run knowledge:retry-failed
```

이 명령은 공공 API와 추가 Finlife 실패 요청을 재시도한다. 은행·저축은행 기본 수집이나 정부24 등 모든 실패를 자동 복구하는 명령은 아니다. 해당 단계 실패는 원인을 고친 뒤 전체 회차를 다시 실행한다.

같은 한국 날짜에 필요한 입력이 모두 수집·점검됐음을 확인한 경우에만 `npm run knowledge:refresh -- --from prepare`로 통합 단계부터 재개할 수 있다. 날짜가 바뀌었거나 필수 입력이 없으면 전체 갱신을 다시 시작한다. 파이프라인은 재개 전 필수 입력 날짜를 검사한다.

| 상황 | 조치 |
| --- | --- |
| 일시적인 통신 실패 | 실패 요청만 재시도하고 이전 성공 자료 유지 여부 확인 |
| 401·403 또는 키 부재 | 키의 승인·권한·유효 상태 확인, 비밀값을 로그에 붙이지 않음 |
| 호출량 제한 | 제공기관 제한을 확인하고 재시도 시점을 늦춤. 무제한 반복하지 않음 |
| 스키마 변경·페이지 누락·ID 충돌 | 해당 출처 신규 자료 반영을 보류하고 수집기 또는 매핑 수정 |
| 공식 API 미제공·미연결 | 정기 갱신에서 제외하고 사유 기록. 웹 수집으로 자동 대체하지 않음 |
| 목록에서 기존 항목 미확인 | 과거 기록과 날짜 보존, 판매 종료·폐지를 단정하지 않음 |
| 배포 전 필수 검사 실패 | 이번 변경의 운영 반영을 중단하고 직전 정상 서비스 유지 |

일반 운영 재시도는 원인 확인 후 한 차례를 기본으로 한다. 추가 시도는 결과와 기관 제한을 보고 결정한다. 이는 현재 수집기의 내부 재시도 횟수와 별개의 운영 규칙이다.

## 7 검토와 서비스 반영

금융자료·온톨로지 담당은 ID·관계 보존, 신규·변경·미확인 항목, 공식 근거와 날짜를 확인한다. 독립 품질검증 담당은 스키마·관련 회귀·무료 MCP 검사와 보안 조치 결과를 확인한다. 화면·사용자 경험 담당은 변경 범위의 검색과 상세 화면을 점검한다. 개발보안 담당은 변경에 따른 보안 영향을 검토한다. 배포·운영 담당은 검증된 변경을 사용자 승인 범위 안에서 반영하고 운영 확인·증적을 남긴다. 프로젝트 총괄 PM은 이 결과를 취합해 완료를 판단한다. 구체적인 검사 명령은 [개발 매뉴얼](development.md)의 변경 유형별 검사를 따른다. `knowledge:refresh`에 포함되지 않는 새 검색 검사도 별도로 실행한다.

회차 상태는 다음처럼 구분한다.

| 상태 | 판정 |
| --- | --- |
| 수집 중 | 단계가 아직 종료되지 않음 |
| 검토 대기 | 산출물이 생겼지만 내용과 검사가 확정되지 않음 |
| 부분 갱신 | 일부 출처 실패·보류가 있고 해당 범위를 명시함 |
| 검증 완료 | 이번 반영 범위의 자료와 검사가 통과함 |
| 운영 반영 완료 | 대상 커밋 배포와 실제 서비스 검사가 확인됨 |
| 반영 보류 | 중요한 데이터 오류나 필수 검사 실패가 남음 |

부분 갱신은 실패 출처의 이전 정상 자료와 원래 날짜를 보존하고, 실패 범위가 성공 자료를 오염시키지 않았다는 검토가 끝난 경우에만 선택적으로 반영한다. 부분 실패를 숨기고 전체 최신화로 표시하지 않는다.

배포 범위는 main에 실제 반영할 전체 차이로 판단하고 각각 기록한다. 무료 MCP는 배포 시 포함된 세금 카탈로그를 사용한다.

| 변경 범위 | 홈페이지 | MCP |
| --- | --- | --- |
| 화면 문구·배치·브라우저 동작 | 배포 및 변경 화면 확인 | 재배포 불필요 |
| 공개 자료 갱신, 세금 번들 입력은 동일 | 배포 및 자료·날짜 확인 | 재배포 불필요 |
| `docs/opentax/korea-tax-ontology-2026.json` | 배포 및 자료 확인 | 재빌드·배포 및 SDK 검사 |
| MCP 코드·의존성·설정 | 공개 화면 변경 여부로 판단 | 검증·배포 및 SDK 검사 |
| 지침·팀 매뉴얼만 변경 | 불필요 | 불필요 |

MCP workflow는 `mcp/**`, 세금 원자료, workflow 자체 변경에 반응한다. workflow 자체를 수정하는 첫 반영에서는 MCP 검증·배포가 실행되지만, 이후 홈페이지만 수정한 커밋에는 실행되지 않는다. 기존 미배포 MCP 개선까지 함께 반영하는 경우도 MCP 배포 대상이다. 홈페이지 자료 변경을 MCP 갱신 완료로 보고하지 않는다.

API 키는 비공개 수집 환경·서버 secret에만 보관한다. 공개 파일·브라우저 요청·URL·로그의 노출을 점검하며 비밀값은 보고하지 않는다. 노출 발견 시 공개 반영을 중단하고 키 폐기·재발급 및 공개 파일·Git 이력 정리를 별도 대응한다.

## 8 배포 후 확인과 복구

MCP가 배포 대상일 때의 경로는 [무료판 배포 안내](../mcp/FREE-DEPLOYMENT.md)를 따른다. `OpenFin MCP pipeline`의 validate·deploy·실제 SDK 검사 결과를 확인한다. 새 검색 검사 workflow의 통과 여부도 별도로 확인한다.

현재 배포는 자동 롤백을 제공하지 않는다. 업로드가 끝난 뒤 운영 검사가 실패하면 새 코드가 이미 올라가 있을 수 있다. 이때 실패 표시만 보고 이전 정상 버전이 유지된다고 판단하지 않는다.

배포된 커밋과 일치하는 로컬 체크아웃에서 수동 운영 MCP 검사가 필요하면 PowerShell로 실행한다. 다른 자료 버전의 로컬 파일로 검사하면 체크섬 불일치가 날 수 있다.

```powershell
$env:MCP_URL = 'https://openfin.cocomo0412.workers.dev/mcp'
node mcp/scripts/smoke-free.mjs
Remove-Item Env:MCP_URL
```

홈페이지만 변경한 작업에서는 해당 화면과 자료 요청을 검사하며 MCP 재배포·전체 운영 검사를 반복하지 않는다. 홈페이지에서는 첫 검색, 변경 항목 상세, 출처 링크, 분야 전환을 확인한다. `/health`가 응답하는지만 보지 말고 MCP의 검색·조회와 대상 자료 버전까지 확인한다.

잘못된 반영이 확인되면 영향 범위를 기록하고 신규 반영을 멈춘다. 문제가 생긴 코드·데이터·생성물을 함께 되돌리는 수정 또는 revert를 별도 브랜치에서 준비해 검증한 뒤 새 main 커밋으로 반영한다. 마지막 정상 커밋의 실행을 그대로 재시도하면 최신 main의 MCP 입력 비교에서 막힐 수 있으므로 과거 workflow 재실행을 복구의 기본 수단으로 삼지 않는다. 복구 후 실제 반영 대상인 홈페이지 또는 MCP를 검사하고, 둘 다 바뀌었다면 각각 검사한다.

직전 정상 커밋만으로 Git 제외 수집본까지 복원되지는 않는다. 이전 자료가 필요하면 보호된 수집본 또는 다시 수집한 검증 자료를 사용하고, 기존 날짜를 오늘 날짜로 바꾸지 않는다.

## 9 기록과 보고

회차마다 다음 양식으로 비밀값을 제거한 기록을 남긴다. 변경이 없더라도 점검 사실과 실제 재조회 범위를 기록하며, 사용자 알림은 중요 변경·실패·조치 필요 사항 중심으로 운영한다.

```text
회차 시작 시각과 한국 기준일:
실행 담당과 검토 담당:
기준 커밋 / 반영 커밋:
예정 출처 / 실제 점검 출처 / 건너뛴 출처:
성공 요청 / 실패 요청 / 보류 요청:
추가 항목 / 변경 항목 / 목록 미확인 항목:
날짜와 검토 범위의 변경:
검사 결과와 증거 위치:
반영 범위와 유지한 이전 자료:
홈페이지 배포 필요 여부 / 이유 / 반영 커밋 / 운영 확인:
MCP 배포 필요 여부 / 이유 / 반영 커밋 / 운영 확인:
API 키 노출 점검 범위 / 발견 여부 (값 기록 금지):
미해결 사유 / 담당 / 다음 조치:
최종 상태:
```

출처 점검 Actions의 현재 artifact 보관 기간은 3일이므로 금요일 실행 결과를 다음 화요일까지 보존한다고 보장할 수 없다. 정기 운영 도입 전 비밀값을 제거한 회차 기록과 검토 근거를 저장소 또는 승인된 보관소에 보존한다. 운영 기록 최소 90일 보관을 제안하며, 원자료 보관은 출처 이용조건과 저장 용량에 맞춰 별도로 정한다. 보관 기간 설정은 이번 문서 작성에서 변경하지 않았다.

## 10 자동 실행 도입 전 남은 준비

주 2회 일정은 정해졌지만, 실제 자동화는 별도 작업이다. 연결된 실행 환경과 키, 이전 성공 수집본 보관, 동시 실행 방지, 실패 보고, 검토 대기열을 먼저 확인한다. 로컬 채팅 예약과 서버 실행은 가용 조건이 다르므로 사용할 실행 방식을 선택한 뒤 구현한다.

첫 도입은 공식 API의 정기 수집·검증과 검토 보고까지 자동화하고, 검토된 자료를 기존 배포 경로로 반영하는 방식으로 시작한다. 웹 수집 대체 경로를 자동화에 연결하지 않는다. 무인 갱신·검토·배포 전체가 이미 구현됐다고 표시하지 않는다. 예약을 켠 뒤 실제 첫 회차의 기록이 생겼을 때 작동 여부를 확인한다.

근거 코드: [전체 갱신](../scripts/knowledge/refresh-all.mjs), [공공 API 갱신](../scripts/knowledge/refresh-public-apis.py), [수집 계획](../scripts/knowledge/public-api-refresh-plan.json), [출처 점검](../scripts/knowledge/track-sources.mjs), [출처 점검 workflow](../.github/workflows/track-sources.yml).


## 개선점 탐색 증적 관리

사용자가 요청한 개선점 탐색은 [발견일별 기록](../reports/improvements/README.md)에 남긴다. 한국시간 날짜별 폴더에 재현 단계·기준 커밋·화면/코드 증적·우선순위·상태를 기록하고, 같은 문제는 ID를 유지해 수정·운영 재검증 결과를 연결한다. 발견일은 원자료 수집일과 구분하며 과거 증적을 소급 생성하지 않는다. 화면에 공개된 자료만 증적으로 보존하고 키·개인정보는 포함하지 않는다. 탐색 기록만 추가한 작업은 홈페이지·MCP 배포와 분리해 보고한다. 이 절차 추가가 자동 실행 예약 활성화를 뜻하지 않는다.
